# 2026-09-07: two findings about method, from the rename plan's review loop

Both come from one artifact, `docs/plans/rename-to-agentdataentry.plan.md`, which ran **four Codex
review rounds where the standing loop specifies one**. Eleven findings, six of them blocking. The
artifact is the evidence for both entries below and is worth reading beside them.
⚠️ **That plan is on branch `rename-agentdataentry` and is not merged as this is written**, so
its round history and quoted criteria are inspectable only from that branch until it lands.
Nothing below depends on reading it: every figure here names the scope and the head that
produced it.

Neither finding is about renaming. They are about **how a property gets bounded** and **what a
review round can and cannot check**, and they are recorded here because the next build meets both.

---

## ⭐ 1. Bound a property over its REACH, not over its MEANING

The contract already says an unbounded property cannot be closed by review and must be bounded.
**It does not say how.** This is one move that worked, stated so it can be reused.

### The property that would not close

Section 6 of the plan rested on:

> *No statement about the past is falsified by the sweep.*

A rename rewrites the project's name everywhere. Some of the places it appears are **records of
things that happened** -- a captured traceback, a quoted error, a ruling citing a file that existed
under that name -- and rewriting those makes a true statement false.

**That is a universally quantified negative over an unbounded input space, and it behaved exactly
as the contract predicts.** Three rounds, three instruments, three genuine misses:

| round | instrument | what it missed |
| --- | --- | --- |
| 1 | keyword `grep` piped into a second `grep` | it matched the **file path**, so every file under the package directory satisfied the filter by its own path. Returned **101** lines against a claim of **1**; content-only matching returned 3 |
| 2 | token-scoped: `COMMENT`/`STRING` tokens carrying a past-tense marker | a docstring whose only markers were the plain words `was` and `replaced` |
| -- | any classifier at all | see below |

⚠️ **Round 2's miss is the one that proves no classifier ABOVE THE OCCURRENCE can work.** In that docstring, the
surrounding sentence is **present-tense behaviour that SHOULD be swept**, while the quoted error
string inside it is **a captured observation that must not be.** They are in one paragraph. No
file-level, document-level, or marker-level classifier separates them, because the distinction is
not a property of any container the text sits in.

⛔ **That is a claim about granularity, not about automation, and the difference matters to
whoever reads it next.** A classifier operating at the occurrence itself is exactly what the
accounting below is, and it separated that paragraph correctly. **Do not read this entry as a
reason to prefer hand judgement over a finer-grained instrument**; read it as the reason the
unit has to be the occurrence. Where a finer instrument can decide an occurrence, use it, and
spend the hand judgements on what it cannot.

### The move

**The property was unbounded over the text's MEANING. It became bounded over the sweep's REACH.**

> **The sweep cannot falsify a statement it does not rewrite.**

The sweep only rewrites occurrences of one string, and **those are countable**. So the criterion
stopped being *"is this statement about the past?"*, which requires judgement over an unbounded
space, and became *"is every occurrence dispositioned exactly once?"*, which is an accounting over a
finite set.

What that bought, concretely:

- **A complete input space.** 572 occurrences, partitioned into six classes that sum to it, so
  completeness is arithmetic rather than argued.
  ⚠️ **Scope and head, because this document's second entry demands them:** in scope means the
  repository minus the plan page itself, and the head is `B`, the commit the build started
  from. The same census over the whole repository at that head is 666, and the difference is
  the plan page's own 94 occurrences.
- **An arithmetic exit condition.** The dispositions must equal the census command's own output as a
  set, `comm -3` empty in both directions.
- ⭐ **A finding with a fixed point.** A reviewer can now say **"entry 137 is wrong"**. That is one
  claim about one occurrence, it is answerable, and answering it does not create new surface. Under
  the old property a reviewer could only ever say *"here is another statement you would falsify"*,
  forever, and every one of them was correct.

### Two conditions, both learned the hard way in the same loop

- ⚠️ **The key must identify ONE element of the set, and the exit condition must be set equality,
  not equal totals.** Round 3 found the first version keyed a disposition by `path:line`, and
  **13 lines carry more than one occurrence** (572 occurrences over 557 lines, in scope at `B` =
  `cf3a15b6b5fbddf217afb4daa2552bc9c03af015`; the same measure over the **whole repository** at
  `c759ac2`, an earlier commit on the same branch, read 19 lines and 655 over 633). ⚠️ **Those
  two figures differ in head AND in scope**, and both differences are the plan page: it held 83
  occurrences at `c759ac2` and 94 at `B`, which is why the second entry below asks for the head
  and the scope together rather than either alone.

  Two entries could collide on one occurrence while a third went unrecorded and the total still
  balanced. The key became `path:line:column`, **emitted by the census command itself** so the
  build can actually produce it: measured injective, 572 rows to 572 distinct keys.
- ⚠️ **The bounded criterion must be executable.** A bound nobody can perform is worse than an
  honest recorded residual. The cost here is 321 individual judgements, which was weighed and
  accepted; a cheaper boundary was measured and rejected because it dropped one of the three
  known cases. ⚠️ **321 was the plan's prediction and the build performed 323**, the two extra
  coming from an f-string that tokenizes differently on 3.12 than on 3.10, so even the cost of
  a bounded criterion is a figure to re-measure rather than inherit.

### ⛔ The residual, recorded rather than hidden

**The accounting proves every judgement was made and recorded. It does not prove each one is
right.** That is a real weakening and it is the price of a criterion that closes. What makes it
acceptable is that the remaining risk is now discoverable by **doing** the work rather than by
reviewing prose about it: only the build performs the dispositions, so only the build can find
that one of them is wrong.

**That is also why the loop stopped.** A fifth review round would have reviewed prose about a sweep
nobody had run.

## ⭐ 2. A wrong number given to a review round survives every round it is given to

### What happened

The plan's Context section said the old name sat in **106** of 147 tracked files. **It is 110.**

The figure came from the inventory probe, was repeated to the owner, and was written into **every
round prompt** under a heading reading *"measured, do not re-derive"*. It survived **four
adversarial rounds**, each of which was sharp enough to find a non-injective accounting key, a
self-contradictory pair of acceptance criteria, and a `grep` that matched paths instead of lines.

**It was found by the fifth revision seat, which re-measured it while checking something else.**

Verified independently: 110 files carry the name on `main`, against a negative control of 0 for an
absent pattern and a positive control of 142. `106` is the count of `.py` files over the four code
trees, a different quantity that other sections use correctly. It had been copied into a sentence
about files-carrying-the-name.

### ⚠️ Why no round caught it

**A reviewer checks the artifact against its premises. It does not check the premises.**

That is not a failure of any round. It is what review is: given a set of stated measurements, find
where the artifact contradicts itself or breaks. **A premise handed over as measured ground truth is
outside the thing being reviewed**, and a *"do not re-derive"* heading -- which exists for a good
reason, since re-deriving prior dispositions is what made an earlier branch run to 27 rounds --
makes it explicitly so.

⛔ **So the more disciplined the review ledger, the more securely a wrong premise sits inside it.**

### What to do about it

- **The build is the first component that runs the thing, so the build re-measures the figures it
  depends on**, each against a positive control, and reports any that disagree. A stale figure is a
  finding, not an embarrassment.
- ⚠️ **This sharpens the existing count rule rather than repeating it.** That rule says a documented
  count goes stale silently and must say whose count it is. This adds: **a count handed to a
  reviewer as a premise cannot go stale silently, because nothing in the loop is looking at it at
  all.** The two failure modes are different -- one drifts under observation, the other is never
  observed.
- **State premises as what they are.** A figure in a review prompt is a number somebody measured at
  some head, and the prompt should say which head. This plan now labels every whole-repository count
  with the head it was measured at, after that count moved four times: 572, 636, 652, 655, 666,
  every move caused by the plan document's own growth inside its own measurement scope.

## ⭐ 3. `git grep --column` reports a column that is not the column

**Version, so this can be re-measured rather than trusted: git `2.53.0.windows.1`.**

This is the recorded class again -- **a check whose definition comes from the tool rather than from
the specification** -- and it earns its own entry because `git grep` is used constantly here, and
because a plan's correctness argument rested on it.

### The input and the wrong output

At `B`, `tests/unit/test_host_plugin.py:192` reads:

```
    assert covered == {"gramps_live_api_host.py", "gramps_live_api_host.gpr.py"}
```

Two matches. `git grep -o -n --column` reports them at columns **25** and **64**. Computing the
offsets from the line itself with `grep -b -o` gives **25** and **52**.

**The first is right and the second is wrong by twelve.** Reproduced on other lines with the error
in both directions, so it is not a fixed offset and not a one-off: reported values have been both
higher and lower than the truth, and some are correct.

### Why it mattered

The rename plan keyed each of 572 dispositions by `path:line:column` and argued injectivity **a
priori**: *two matches cannot begin at the same column of the same line of the same file.* That
argument is sound about columns and **says nothing about this field**, because the field is not the
column.

Two consequences, both real:

- **A reviewer following `tests/unit/test_host_plugin.py:192:64` lands on the wrong part of the
  line.** The key is not a locator, though it reads exactly like one.
- **A build that joins its ledger to the tree by that column misclassifies.** The rename build hit
  this: joining by the reported column left a key unmatched, and joining by **ordinal on the line**
  made the join total at 351 keys with 0 unmatched either way.

**Injectivity is still true here, but only as a MEASUREMENT** -- 572 rows, 572 distinct keys,
re-measured -- **not as the argument the plan made for it.** A property that happens to hold and a
property that was proved are different things, and only one of them survives a change of input.

### How to re-measure it

```
git grep -o -n --column -i -E -- '<pattern>' <rev> -- <path>      # what git reports
git show <rev>:<path> | sed -n '<line>p' | grep -b -o -E '<pattern>'   # the true byte offsets
```

⚠️ The second command's offsets are **0-based** and git's are **1-based**, so a correct match shows
as a difference of exactly one. Anything else is the defect.

## Two operational facts about running these gates, recorded so they are not re-diagnosed

Neither is a finding about the rename. Both change how the next review round should be scheduled.

### The reviewer's REACH is a separate lever from the review's SCOPE

The first attempt at the rename build's code round **exhausted a Codex usage window without
producing a verdict**, at 858,103 bytes. It was reading the Gramps installation.

The round was then scoped: told to review the disposition ledger rather than the 127-file diff,
given the arithmetic and the gate results as established facts, and told not to read the Gramps
installation. **It completed inside one window**, 32 minutes, 1,129,225 bytes, with 64 reads of the
accounting.

⚠️ **But the scoping is NOT what stopped it reading Gramps.** Measured as exec commands actually
targeting that installation: **6 in the scoped round against 7 in the dead one.** That is the same
behaviour, not reduced behaviour. What the scoping changed is where the bulk of the work went, into
the ledger, and that is why it finished.

⛔ **So if a round dies on the window again, the fix is NOT more scoping of the diff.** The
instruction not to read a path did not reduce reads of that path. **Exclude the Gramps installation
from the reviewer's reach explicitly**, by sandbox or by configuration, rather than by asking.

⚠️ **And a warning about the measurement itself, since it was got wrong once here.** Counting lines
that *mention* the installation gives 226 for the dead round and 1001 for the scoped one, which
reads as a large increase and is meaningless: most of those lines are output content echoing paths.
**Count exec commands that target it.** This is entry 3's shape again, a convenient field answering
a different question from the one it appears to answer.

### The pull request bot and the command line draw on SEPARATE budgets

**Measured: bot round 2 on this pull request landed on head `5ebf92b` while the Codex command line
was refusing every invocation with `You've hit your usage limit`.**

⚠️ **A brief that omits an accepted item invites the next seat to re-find it.** The second review
seat raised a tool naming a repository that does not exist yet. That is the release sequence working
as designed, the repository is renamed before the branch is pushed, and it was accepted. **It was
raised because the brief listed the other accepted items and not that one.** A reviewer cannot
accept what it was never told was decided, and every seat after it will spend the same effort.

⭐ **This matters for scheduling, and it matters in one specific direction: the pull request bot gate
is not at risk from the command line's quota.** That gate is the one that precedes the merge click,
so a command-line window being exhausted delays local rounds and does **not** endanger the gate the
merge depends on. Spend the command-line budget accordingly.

## ⭐ 4. The component fails closed. The instruction fails open.

**A test that exercises a COMPONENT when the property is about the INSTRUCTION CONTAINING it.**

### What happened

A page of user-facing documentation told a reader to remove an old plugin junction with
`Remove-Item`. Measured: on PowerShell 5.1 that **does not remove a junction** and `Test-Path` stays
true, so the reader ends with two directories registering one plugin id.

The obvious repair is worse than the defect. `Remove-Item -Recurse -Force` **can follow the reparse
point into the junction's target**, and the target is the reader's own checkout. Measured, it
removed the junction and left the target intact -- which is luck, not a guarantee, and not a
property to put in documentation.

The replacement was `[System.IO.Directory]::Delete($path, $false)`. The `$false` is non-recursive,
so it **cannot** follow the junction by construction, and it **refuses** a real non-empty directory
rather than emptying one. The fix round was asked to demonstrate both, and did:

```
junction   -> removed, target's files survive
directory  -> refused, System.IO.IOException: The directory is not empty
empty dir  -> deleted   (the control, so the refusal is a real refusal)
```

**All true. All about the wrong thing.**

### The defect

The next review round ran **the documented block**, as a reader would paste it:

```
Exception calling "Delete" with "2" argument(s): "The directory is not empty."
old junction removed          <- printed anyway
  directory still present: True
```

The exception is **non-terminating**. The next statement runs and prints success over a directory
that survived. A second input state was worse: if the preceding snippet threw before assigning
`$plugins`, the block expands the path to `\gramps-live-api`, finds nothing, and prints **"no old
junction, nothing to do"** while the old junction sits there.

⛔ **Two false cleans, in user-facing documentation, about deleting things.**

### The rule

> **When the property is about an instruction, the acceptance criterion is running the instruction,
> verbatim, in every input state it documents. Exercising the component inside it proves something
> else.**

⚠️ **The gap is invisible from inside the component test, because the component test passes and is
correct.** `Delete` really does fail closed. What fails open is the block, and nothing about the
call's behaviour reveals that.

**This is the session's recurring class in a new place**: a check whose definition comes from
somewhere other than the specification. Here the specification is *"the reader ends with one
junction"*, and the check answered *"does this .NET method refuse a non-empty directory"*.

## ⭐ 5. Tense governs, not whether the string exists today

**A discriminator for deciding whether an occurrence in prose is historical.**

A rename sweep must not rewrite statements about the past. A fix round proposed this rule for
deciding which occurrences are historical:

> *A thing that still exists is named by its current name; a thing that was retired is named by the
> name it had while it existed.*

**It is right in general, and it was wrong on the line it had just checked and cleared.** The
docstring reads:

> *The first version of this check asked `isdir(candidate/"gramps_live_api")` and stopped. An empty
> or partial directory satisfied it, `check` printed ready, and host startup would then have died on
> `from gramps_agent_data_entry.host import accessor, service`.*

The import **does** exist today, verbatim, in the plugin. Under the existence rule it is a live
citation and stays swept. But the clause sits inside a **counterfactual about the first version's
era**, when the package had the old name. One sentence, two eras, contradicting itself.

> **The corrected discriminator: TENSE GOVERNS, NOT WHETHER THE STRING EXISTS TODAY. A clause inside
> a past-tense counterfactual names its own era.**

⚠️ **Note where this was found.** The fix round had been told explicitly to check the neighbours of
each freeze for exactly this incoherence, examined this line, and cleared it with a stated reason.
**A neighbour check with a wrong discriminator produces a confident clear**, which is worse than no
check, because the next reader sees the line was considered.

## ⭐ 6. An ARTIFACT can be unbounded the same way a claim can, and the fix is the same

The existing rule is about **claims**: a universally quantified negative over an unbounded input
space has no fixed point, so review cannot discharge it, and the answer is to bound it. Entry 1 is
that rule applied to a specification.

**This is the first time it has been about INPUT STATES rather than about a claim.**

### What happened

A page of user-facing documentation carried a PowerShell block the reader pastes into a console. It
had to behave correctly in every state that console might already be in. **Three consecutive review
rounds found it wrong in four different states, and each one was a state nobody had enumerated the
round before:**

| round | the state |
| --- | --- |
| 1 | `Remove-Item` does not remove a junction at all, and `Test-Path` stays true afterwards |
| 2 | the variable holding the path is unset, because the preceding snippet threw, and a throw in a pasted block does not stop the lines pasted after it |
| 2 | a real non-empty directory: the deletion raises a **non-terminating** error and the next statement prints success over a directory that survived |
| 3 | that variable is **stale**: non-empty, pointing somewhere that does not exist, so the block reports nothing to do while the thing is still there |

⛔ **A fifth was never measured by anyone.** A fix round reported that an `else` beginning its own
line parses as a separate statement when pasted, so that branch never ran in any state, while the
identical text saved to a script file works. **Two independent harnesses failed their own multi-line
positive control** and could neither confirm nor refute it.

### Why it could not close

**A block pasted into a reader's console inherits an unbounded prior state.** The set of things that
console might already hold is not enumerable by the person writing the block, which is why each
round found a state the last had not thought of. **The rounds were not converging on correctness;
they were sampling.**

⚠️ **And the fifth finding is the sharper half.** The artifact's real usage mode is *pasted into a
console*, and neither party could execute that mode reliably enough to measure it. **An artifact
whose behaviour in its actual usage mode cannot be measured is not closable by review at any round
count**, however many rounds are permitted.

### The resolution, which is entry 1's

**Replace the unbounded thing with a bounded one.** The block was deleted, not repaired, and
replaced with prose: run the tool that already prints the directory, then delete the folder named
inside it. No variable, no branch, nothing pasted.

> **A sentence has one state.**

⭐ **The tell, available before a round count runs out:** if consecutive rounds each find a defect in
the same artifact and each one is **a new input state rather than a new mistake**, the artifact's
state space is not enumerable by the people reviewing it. That is a signal to replace it, and it
arrives earlier than any ceiling.

⚠️ **Retired, not resolved.** The unmeasurable fifth finding is recorded as retired by replacement.
Nobody measured it and, the block being gone, nobody now needs to. **The distinction matters in the
record**: writing it down as resolved would claim a measurement that was never made.

## ⭐ 7. A measurement about REMOVAL must run where the removed thing cannot be found by another route

**The mechanism, named exactly, because it is invisible and it is common:** the primary checkout's
virtual environment carries an **editable install**, whose `.pth` file holds the path
`<checkout>\src`. That checkout is on `main`, where the old package still exists. **So any
interpreter started from that environment imports the old package happily**, no matter which branch
is checked out anywhere else.

### What it cost

A review found that after the rename, an already-installed git pre-push hook still invokes
`python -m <old package>.core.pii_guard`, which no longer exists. **The conductor tried to reproduce
it twice and twice measured it harmless**, because both attempts used an interpreter from the
primary environment, which resolved the old package through the editable path and exited 0.

It reproduced only through the worktree's own environment, which holds the new package alone:

```
old module, worktree interpreter ....... exit 1, "Error while finding module specification"
new module, SAME interpreter ........... exit 0   <- the positive control
old module, primary interpreter ........ exit 0   <- the contamination
```

⚠️ **The third line is the finding.** It is not a broken instrument in any way that announces itself:
the command runs, the guard executes, the output is real, and the exit code is honest about what it
did. It answers *"can this interpreter find a module by that name somewhere"* while the question was
*"does that module still exist in this change"*.

### The rule

> **A measurement about whether something was REMOVED must run in an environment where the removed
> thing cannot be found by another route.** Name the interpreter, and show a positive control through
> the same one.

⭐ **The positive control is what makes it checkable.** Exit 1 alone proves nothing, since a broken
environment fails everything. **Exit 1 on the old name and exit 0 on the new name, through one
interpreter, is the pair that discriminates.**

### Where else this bites

This is the same class as entry 3, an instrument answering a different question from the one it
appears to answer, with a specific and recurring mechanism: **resolution order**. Earlier in the same
session, a sweep for symbols a retirement had deleted counted stale `__pycache__` bytecode as live
source, and would have kept seven resolved issues open. **Compiled leftovers and editable installs
are the same hazard**: both let a name resolve after the thing it names is gone.

⛔ **And it is worse than an ordinary false negative, because it points the wrong way.** A broken
instrument reporting failure gets investigated. **An instrument reporting that a removal is harmless
gets believed and shipped.**

## What the seven have in common

The first is about a criterion with no fixed point. The second is about an input to review that
review never examines. The third is about a field that answers a different question from the one it
appears to answer. The fourth is about a test that answers a different question from the one that was
asked. The fifth is about a rule that is right in general and wrong where it was applied. The sixth
is about an artifact whose input states could not be enumerated by anyone reviewing it. The seventh is
about an environment that could still resolve what the change had removed.

**All seven are ways a loop can run correctly, round after round, and still not be checking what it
believes it is checking** -- and in each case every individual round was justified, which is what
makes them hard to see from inside one. ⭐ **Three of the five were found by running something that
had already been reasoned about.**

⚠️ **A note on this file's own footprint, because the rename accounting cares.** Entry 3 quotes a
source line verbatim as its input, and that line contains the old project name twice. So unlike the
first two entries, **this document is no longer inert to the rename**: it holds 2 occurrences. It
sits in `docs/reviews/`, which that change banners rather than sweeps, so the two are correct to
leave frozen -- but if this merges before the rename branch, that branch's derived banner set was
computed at its own base and would need this file added. **Merging this after the rename avoids the
question entirely.** The quote is kept because an input nobody can reproduce is not evidence.
